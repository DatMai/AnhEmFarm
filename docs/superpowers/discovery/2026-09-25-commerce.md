# AnhEmFarm commerce — discovery and proposal

Status: historical discovery. Owner approved commerce scope and COD, explicitly selected Node.js + TypeScript instead of Django, and confirmed approval. Current spec: `../specs/2026-09-25-commerce-design.md`, awaiting document review. The alternatives below preserve the original discussion; they are not current implementation authority.

## Owner's request

Complete the website with real customer registration/login, product browsing and purchasing, seller product/user management, sales and order tracking, complete pages/content/effects, production operation, and original Superpowers workflow. Preserve the practical approach, red brand, and existing product families. The owner subsequently selected English for all app and documentation content, with Vietnamese localization deferred.

## Findings

The current site is a frontend prototype. Authentication, persistence, authoritative pricing, inventory transactions, order ownership and admin authorization need a backend. Existing generated images and provisional content cannot establish real product claims.

## Historical architecture options — Node.js was subsequently selected

1. **Rejected after discussion: existing React frontend + Django 5.2 LTS + PostgreSQL.** This would reuse Django's authentication and admin features, but split development between TypeScript and Python. The owner explicitly selected Node.js instead.
2. **TypeScript throughout: React + a Node backend + PostgreSQL.** One language across the repository. Authentication and administration require additional library choices and application work. A viable alternative if a single language is the stronger priority.
3. **Hosted commerce platform with a custom storefront.** Reduces ownership of commerce infrastructure, but introduces provider fees, constraints and a larger dependency on that platform. It is a weaker match for the owner's learning and source-control goals.

Historical research: [Django supported versions](https://www.djangoproject.com/download/), [Django authentication](https://docs.djangoproject.com/en/5.2/topics/auth/). The current approved direction and proposed implementation are in the written specification.

## Proposed release scope

- Public pages: home, category/catalog with search/filter/sort/pagination, product detail with variants, about, contact, shipping/returns/privacy/terms, 404 and recoverable error states. Policy/business content must be supplied or explicitly approved before publication.
- Customer: email registration, verification, login/logout, password reset, profile and addresses, cart, checkout, confirmation, order list/detail with status history and controlled cancellation.
- Seller: authenticated dashboard, product/category/variant/image management, price and inventory editing, customer search and account suspension with audit history, order fulfillment and payment-status recording, sales summaries with explicit date/status definitions.
- Default proposed purchase method: cash on delivery (COD). Confirm address, shipping fee and order total on the server. A live online gateway is a separate integration decision requiring a chosen provider and merchant credentials; no simulated successful payment.
- Order model: persist item names/SKUs/variant labels and prices as order snapshots, integer VND amounts, shipping snapshot, status history, cancellation/restock rules and separately tracked payment status.
- Correctness: atomic stock checks/decrements, idempotent checkout, validated transition rules, ownership/role checks on the server and protected admin operations. Catalog-only/unconfirmed products cannot be ordered.
- UI: responsive layouts, keyboard/focus support, loading/empty/error/success states, restrained transitions respecting reduced-motion preferences.
- Operations: configuration examples without secrets, migrations, controlled demo seeding, CI checks, deployment instructions, HTTPS/session/security configuration, health checks, logging, backups with a documented restore test and an initial admin provisioning procedure.

## Delivery slices to design and plan

1. Backend and identity foundations, permissions, database and test/CI setup.
2. Catalog administration, customer browsing, variants and inventory.
3. Cart and transactional COD checkout, customer order tracking, admin fulfillment and sales.
4. Content/UX completion and production deployment verification.

These are decomposition proposals, not preapproved implementation tasks. Each slice must have explicit acceptance criteria in its approved spec and a concrete implementation plan before execution.

## Required evidence before a production claim

Tests must exercise unauthorized admin access, cross-customer access, invalid/expired account tokens, server-side total calculation, duplicate checkout submissions, simultaneous purchase of the final stock unit, cancellation/restock, failed transactions and invalid order transitions. PostgreSQL transaction behavior must be tested against PostgreSQL. Browser checks must cover the customer purchase and admin fulfillment journeys, mobile layouts and keyboard use. A local demo or successful build alone is insufficient.

## Historical decision question — resolved by owner

Accept the recommended architecture and scope, including COD for the first complete purchase flow, or specify that a named online payment provider is required for the first release. Shipping rates can be admin-configurable, but production rates and regions must be confirmed before accepting real orders.
